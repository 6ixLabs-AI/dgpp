# Explicit opt-in for W4A4 expert prefill, 2026-10-01

The edits left on the local `w4a4-opt-in` branch implement the policy in
[issue #68](https://github.com/HawkBearPig/dgpp/issues/68): Qwen NVFP4 expert
prefill defaults to W4A16 with BF16 activations. `DGPP_MOE_W4A4=1` opts
into activation quantization. A checkpoint's calibration scales select
the quantizer's global scale but never enable the lossy path by themselves.
The memory planner follows the same policy, reserving the 28.2-MiB standard
Qwen activation workspace only when enabled. Decode remains W4A16.

## Origin and evidence

[PR #50](https://github.com/HawkBearPig/dgpp/pull/50) introduced native W4A4
expert-prefill kernels and enabled them by default for calibrated checkpoints.
Its author reported kernel tests, cold-TTFT gains and BFCL `multi_turn_base`
results: 109/200 with W4A4 versus 113/200 and 115/200 in two upstream runs.
That is model-level evidence and must not be described as absent. Our
[earlier review](2026-09-25-pr50-w4a4.md) checked kernel arithmetic, allocation,
output formats and loader restoration, without a new model-quality campaign.

Issue #68 requires additional paired teacher-forced and task evaluation,
including static and dynamic activation scales, before revisiting the
W4A4 default. A kernel oracle using already-quantized operands checks the
arithmetic of that product; it does not measure the effect of quantizing
activations on model quality. This commit restores the requested opt-in
policy without claiming that the outstanding quality gate passed or failed.

The original local patch was carried from `84028a4` onto merged master
`2058631` in the primary checkout. Follow-up work corrected the evidence
wording, aligned DESIGN and PLAN with the implementation, and added a
functional regression beyond the existing memory-plan tests.

## Validation protocol

Build the actual test targets and serving application before running:

```bash
cmake --preset release -DDGPP_WERROR=ON
cmake --build build-release -j 4 --target \
  qwen_forward_test glm_moe_test moe_w4a4_test dgpp_serve_app
ctest --test-dir build-release --output-on-failure \
  -R '^qwen_w4a4_plan_'
# Run GPU cases serially on idle hardware.
ctest --test-dir build-release --output-on-failure -j 1 \
  -R '^(glm_moe_test|moe_w4a4_test|moe_w4a4_layer_test|moe_w4a4_policy_.*)$'
```

The five memory-plan cases cover unset, zero, one, empty and invalid mode
values; calibrated and uncalibrated tables; the row threshold; unsupported
widths; TP slices; and non-NVFP4 weights. The new GPU policy test changes
calibration scales by eight orders of magnitude on an eligible expert
batch. Default/off outputs must remain bitwise identical. Explicit static
W4A4 must respond to the changed scale; dynamic W4A4 must ignore the static
scale. Every mode must leave the fixed-input decode result unchanged.
This regression fails if calibrated scales silently enable W4A4 by default.

The existing opt-in layer test still exercises both host output formats,
device segmentation, below-threshold fallback and scratch reuse. The direct
kernel suite retains the quantized-operands FP64 oracle. These checks
validate policy and implementation correctness, not task quality.

## Remaining follow-up

Issue #68 stays open for the same-binary, interleaved W4A16/W4A4 comparison:
long enough prompts to enter the expert quantizer, hard-text teacher-forced
probabilities, HumanEval, GSM8K and schema extraction, covering both static
and dynamic scales. Re-enabling W4A4 by default requires a passing committed
record. Moving the mode into a journaled deployment setting is also tracked
there and is not part of this default-policy correction.

The historical PR #50 W4A4 latency measurements describe its recorded mode.
The main September 22 benchmark campaign predates that implementation.
This change publishes no refreshed throughput figures; future NVFP4
comparisons must record the activation mode explicitly. The expected direct
performance tradeoff concerns prefill, while the decode kernels are unchanged.

The separately committed [Qwen workload diagnostics](2026-09-28-qwen-workload-diagnostics/README.md)
are historical operational evidence, with generated token IDs removed.
They cannot substitute for the paired quality campaign.
